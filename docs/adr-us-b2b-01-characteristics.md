# ADR: хранение характеристик товара (US-B2B-01)

## Контекст

При создании карточки товара (`POST /api/v1/products`) продавец передаёт `characteristics: [{name, value}]`. Нужно выбрать модель хранения.

## Альтернативы

1. **JSON-поле в таблице `products`** — один столбец `characteristics JSON`. Просто писать/читать; фильтрация по характеристикам требует JSON-операторов БД и плохо индексируется на SQLite.
2. **Отдельная таблица `product_characteristics` (name/value + FK на product)** — нормализованные строки, простые `JOIN`/`WHERE name=? AND value=?`, легко добавлять новые пары без миграции схемы колонок.
3. **EAV с справочником атрибутов** (`attributes` + `attribute_values`) — максимум гибкости и строгая типизация, но выше сложность запросов, миграций и валидации на этапе CREATED без SKU.

## Решение

Выбрана **отдельная таблица `product_characteristics`**.

## Критерии

- **Сложность фильтрации**: пары name/value выбираются обычным SQL без JSON-path; при росте каталога можно добавить индекс `(name, value)`.
- **Удобство добавления характеристик**: новые характеристики продавца — это INSERT строк, без ALTER TABLE и без поддержки EAV-справочника на первом шаге B2B.

EAV отложена до появления канонических фильтров витрины; JSON отвергнут из‑за слабой индексации и различий диалектов.
